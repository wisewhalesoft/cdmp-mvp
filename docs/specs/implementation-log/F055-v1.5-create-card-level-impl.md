## 架構決策

1. **驗證順序：月跑鎖優先**：spec §5.4 寫入語意 step 6 將月跑鎖排在最後（措辭「依序檢查」較鬆），但實作將 `assertNotLocked()` 放在最前以對齊既有 `deleteCardLevel` / `updateCardLevels` service 慣例。月跑鎖屬 cross-cutting concern，提前 check 不影響語意；已與用戶 Peter 確認。

2. **Toast 訊息位置**：Modal 內部於 mutation `onSuccess` 直接呼叫 `showToast`，不走父層 `runWriteOp`，與 `create-tier-mapping-modal` 樣板一致。父層 `runWriteOp` 仍負責 PUT「儲存門檻」按鈕。

3. **HTTP 狀態碼**：DTO `@Matches` 驗證失敗，經 `HttpExceptionFilter` 將 BadRequest(400) 轉成 **422 + `error: VALIDATION_ERROR`**，符合 spec §5.4 錯誤回應表（422 VALIDATION_ERROR）與 error-handling.md。

4. **dedup 行為（BR-9）**：`findOne` 查 `(cardType, cardVersion, cardLevel)` 命中當前存活紀錄才回 CARD_LEVEL_DUPLICATE。因 §5.3 採 hard delete，紀錄釋放後同 cardLevel 可重新 POST 成功（TS-F055-C11 / P09 regression 覆蓋）。

5. **錯誤訊息上下文**：`SCORING_RANGE_OVERLAP` 帶 `conflictLevel` / `conflictScoreS` / `conflictScoreE` 於 details，供前端顯示「與既有等級 {X} 區間 {Y}~{Z} 重疊」（spec §7 UI/UX 需求）。

6. **regression guard 同步**：`m02-error-code-consistency.spec.ts` 之 `validCodes` 原僅含 v1.4 三個拆分後綴（IN_VERSION / RECORD_NOT_FOUND / REFERENCED），v1.5 新增 `CARD_LEVEL_DUPLICATE` 屬 spec 同步補登，未擴大 scope。
