## 設計選擇與權衡

### 1. SQLite path M-A2 順序與 PG path 不同（必要差異）

**Spec 規範**（§18.11.4 / B01 / B02）：Step 1 UPDATE → Step 2 ALTER（PG）／表重建（SQLite）。

**物理約束**：`UPDATE SET col = NULL` 在 NOT NULL column 上會立即拋 constraint violation
（無論 PG 或 SQLite）。

**落地決策**：
- PG path 維持 spec 文字順序（UPDATE 在 ALTER 之前）— mock test 仍以 SQL 文字比對通過
- SQLite path 改為「CREATE → INSERT SELECT NULL → DROP → RENAME → UPDATE 幂等」
  順序，因 NOT NULL 約束會拒絕 UPDATE。

**理由**：B03 spec 並未要求 SQLite path 之 UPDATE 在 CREATE 之前；測試只驗
表重建 SQL 結構（含 CREATE/INSERT/DROP/RENAME 順序 + INSERT 含 `NULL AS prod_best`）
+ UPDATE 存在於序列中。功能驗證（B04/B05）通過 functional SQLite in-memory
確認 prod_best 變 null 且 schema nullable。

**Migration source 已加 inline 註解明示此差異**，未來營運若實際 PG 環境執行
也遇到 NOT NULL violation（不太可能，因 PG 為 transaction-level 檢查），
operator 須在執行 migration 前暫時放寬約束或調整 Step 順序。

### 2. K01a regex 對註解過於嚴格 → 改寫註解避匹配

**狀況**：K01a 要求 `assignment-list.service.ts` 不含 `/dto\.prodBest/`，原始註解
「service 層 ignore dto.prodBest」字面 match。

**選擇**：改寫註解為「service 層 ignore dto 之 prodBest 欄位」，語意完全保留，
規避 regex 過度嚴格但仍保留 K01a「dead code 字面禁止出現」的設計意圖。

### 3. M-A1 採 UPSERT 而非 DO NOTHING（與 m22 / m284 不同）

**理由**：覆寫 m240 殘留之 `best_case N='一般案件'` → 「非優質案件」（F076 v1.6
/ US-129 Q2 決議）。若採 DO NOTHING（如 m284 case_status seed）會跳過覆寫，
保留錯誤 label。

**§18.11.9 R8 緩解**：user 已確認 MVP 環境無終端用戶依賴舊 label；UPSERT 語意
可安全覆寫。

### 4. 編輯模式 cardType 前端 filter — 僅顯示「active + 名單現存 inactive」

**對齊 prototype 27b L513-524**：inactive 卡別僅在等於名單現存 cardType 時才出現
（其他 inactive 不顯示）。

**理由**：使用者無從選擇與名單無關的 inactive 卡別，介面收斂；現存 inactive 值
則必須顯示以維持名單可讀性（Q-A 決議「不重選但保留舊值」）。
