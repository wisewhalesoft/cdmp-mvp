## 重要技術設計

### 後端 service

| 主題 | 實作 |
|---|---|
| 覆寫式 PUT dimensions | `scoreRepo.delete(...)` → `scoreRepo.save(newRows)`；card_version 不遞增 |
| 區間重疊驗證 | `hasNumericOverlap` / `hasStringIntervalOverlap` 純函式；半開合法（score_e+1 = 下一級 score_s） |
| 月名單分派鎖 | `assertNotLocked()` 共用 helper；In(['pending','running']) |
| audit log entity_id | dimensions: `H\|1\|ACCOUNT_AGE`、card-levels: `H\|1`、tier: `H\|A` 或 `M5\|`（fallback） |
| DISABLE action cast | 沿用 F068 pattern：`'DISABLE' as 'DELETE'`（DB schema varchar(10) 容許） |
| F056 fallback 跳過 active 驗證 | `cardLevel == null` 短路 `assertCardLevelExistsOrFallback` |
| F056 BR-9 | `cardLevel.length > 1` 直接拋 CARD_LEVEL_NOT_FOUND（VARCHAR(1) vs VARCHAR(5) 不對稱保護） |
| F056 findTierByPk | cardLevel=null 時用記憶體 `.find()`，避免 TypeORM where {x: null} 轉成 SQL `=NULL` 不 match |
| preview 計算來源 | `ob_pool_data_list.score`（既有計算結果套用新門檻），非實時呼叫 fn_calc_tier_level |
| 跨層 fn_calc_tier_level | `describe.skipIf(process.env.DB_TYPE !== 'postgres')` 條件跳過 SQLite |

## 後端實作（GREEN）

### Service 層（`apps/api/src/modules/assignment-scoring/assignment-scoring.service.ts`）

- **錯誤碼常數重構**：移除 `CARD_LEVEL_NOT_FOUND`，新增 4 個拆分後常數 + 對應訊息
- **新增 `deleteCardLevel(input, actor)`**：
  - 月名單分派鎖（`assertNotLocked`）→ 複合 PK 存在性檢查 → cascade reference check → `levelRepo.delete({...})` → audit log
  - **Cascade 比對技巧**：`referencingTiers.some(t => t.card_level === input.cardLevel)` — 嚴格 `===` 比對自然排除 fallback NULL 紀錄（NULL !== 'A'），與 spec AC-7 行為一致
- **新增 `deleteTierMapping(input, actor)`**：
  - 月名單分派鎖 → `findTierByPk()` 取 entity → **`tierRepo.remove(entity)`** hard delete → audit log
  - **為何 `remove(entity)` 而非 `delete({card_level: null})`**：避免 TypeORM 將 `{card_level: null}` 轉成 SQL `card_level = NULL`（三值邏輯永不 match），參見 [[feedback_typeorm_null_pk_delete]]
- **重新繫結既有錯誤點**：
  - `updateCardLevels` L745 PK miss → `CARD_LEVEL_RECORD_NOT_FOUND`（404，與 DELETE 共用）
  - `assertCardLevelExistsOrFallback` 三處（length>1 / version 缺 / level 缺）→ `CARD_LEVEL_NOT_FOUND_IN_VERSION`（422）

### Controller 層

- import `Delete` 裝飾子 + 兩個新 DTO
- 新增 `@Delete('card-levels')` + `@Delete('tier-mapping')`，沿用 class 層級 `AuthGuard + SalesManagerGuard + @RequireSalesManager()`
- F056 DELETE 將 query.cardLevel `undefined` 顯式轉 `null`（service 解讀為 fallback NULL 規則）

### DTO 新增

- `delete-card-level-query.dto.ts`：三個必填（cardType / cardVersion / cardLevel），cardVersion 走 `@Transform` Number 轉型
- `delete-tier-mapping-query.dto.ts`：cardType 必填、cardLevel 選填（省略 = NULL fallback；不可空字串，與 BR-9 一致）

## 設計取捨與技術筆記

| 主題 | 決策 |
|---|---|
| 單筆 score 編輯 / 刪除 | 走既有 `updateDimensions` 覆寫式 PUT（前端組整批 scores），不新增 single-score endpoint — 與 F054 BR-3 一致 |
| CardLevels 單列儲存 | check icon 觸發整批 PUT；spec §5.1 三欄複合鍵 UPDATE 對使用者透明 |
| **規格 vs prototype 折衷** | spec F055 §7「整批儲存」vs prototype 28「單列 check icon」採折衷：UI 保留 prototype 的 per-row check 但實際呼叫整批 PUT |
| TierMapping 編輯 | 透過既有 PUT batch UPSERT 送單筆 mapping，PK 唯讀，僅 tierLevel / listNm 可改 |
| Modal 內 cascade 409 處理 | `LevelDeleteConfirmModal` catch 內依 error code 分流：`CARD_LEVEL_REFERENCED` / `CARD_LEVEL_RECORD_NOT_FOUND` → inline 顯示且不關閉；其他（lock / auth）→ runWriteOp toast + 關閉 |
| Fallback NULL 刪除 query | API client 內判斷 `cardLevel !== null` 才加 `params.cardLevel`，避免空字串（F056 BR-9）|
| 錯誤碼常數無 backward alias | 拆分後不保留舊 `CARD_LEVEL_NOT_FOUND` alias，避免 silent fallback；TypeScript 編譯確認無殘留引用 |

## Open points / follow-ups

1. **F055 §5.1 PUT 錯誤碼表未明示 `CARD_LEVEL_RECORD_NOT_FOUND`** — 既有 PUT 實作於 PK miss 時拋 404，與 DELETE 共用此錯誤碼，但 spec 表中未列出。建議 spec-writer 後續補完 §5.1 錯誤回應表（不阻擋本 PR）
2. **`ob_tier` fallback seed migration（M3/HC/C3）未在 docker rebuild fresh DB 中植入** — Step 6 驗收時 `/tier-mapping` 僅見 M5 一筆 fallback。M3/HC/C3 seed migration `1711360000150` 在 v1.0 已寫，但 PO 的 docker rebuild fresh DB 似乎未跑該 migration。建議 PO 確認 `docker-compose` migration runner 配置（或 dev seed script）
3. **F055 DELETE 不限制 cardVersion 必須 active**（PO 2026-05-14 決議：可清歷史版本）— 若日後業務要求僅 active 可刪，需新增 BR-7 與對應 service 驗證
4. **DTO `cardVersion=非數字` 邊界**（如 `?cardVersion=abc`）由 NestJS ValidationPipe 自動回 422 VALIDATION_ERROR — 未補 E2E（屬框架行為），若需明確覆蓋可加 `TS-F055-D14`
5. **vitest assertion 對 className hover 色斷言用 hex 色（如 `hover:text-[#2563EB]`）而非 Tailwind 命名色** — 配合 page.tsx 既有色彩約定，未來若統一改 Tailwind theme token 需同步調整
