## Architectural Decisions

### A1. F076 archived 採方案 C（MVP 不實作）

**決策**：F076 spec §7 [DEFERRED] 標記 F076-M5 archived 欄位 UI 區塊。

**理由**：

1. 完全不動 backend（user 約束 #1）— 方案 A 需新 endpoint「listFieldsWithOptionsButNotCategorical」、方案 B 需 N+1 query
2. 零商業價值損失：F051 既有名單編輯透過 BR-12 `includeInactive=true` 已可查詢 inactive options
3. 純為「讀取展示」，非月跑必須

### A2. F075-M8 / F075-M9 不實作

**決策**：F075 spec §7 [DEFERRED] 標記 F075-M8（scope 提示區塊）+ F075-M9（seed 來源 column）。

**理由**：

- M8：React 既有「管理 OBPOOLDATA…」描述行已替代 scope 資訊；增加 box 屬視覺重複
- M9：後端 entity 無 `seed_note` 欄位；屬 backend schema change，超出 v1.4.5 範圍

### A3. CategorySwitchConfirmModal 重用，不重新實作

**決策**：Edit Modal 中「categorical → numeric/date」切換時觸發既有 `CategorySwitchConfirmModal` 元件。

**做法**：父層 `field-whitelist-page` 收到 EditFieldModal submit 後偵測級聯場景 → 暫存 `pendingEditPayload` state → 渲染既有 component（reuse）。

### A4. F076 reactivate field_type_changed 攔阻採前端純 UX 攔截

**決策**：點 `btn-reactivate-{optionValue}`（`deactivatedReason === 'field_type_changed'` 之 option）時，**不**呼叫 `reactivateOption` API，改顯示 warning toast。

**理由**：避免 backend 不必要 round trip；UX 清楚告知使用者正確操作路徑（先於 F075 將欄位類別改回 categorical）。

### A5. Toast 全部以 displayName 為主（沿用 v1.4 AC-15）

各成功 toast 字串：

- F075 新增：「欄位『{displayName}』已新增」
- F075 編輯：「欄位『{displayName}』已編輯」
- F075 停用：「欄位『{displayName}』已停用」
- F075 啟用：「欄位『{displayName}』已啟用」
- F076 新增：「可選值 {optionValue} 已建立」
- F076 停用：「可選值 {optionValue} 已停用」
- F076 啟用：「可選值 {optionValue} 已重新啟用」
