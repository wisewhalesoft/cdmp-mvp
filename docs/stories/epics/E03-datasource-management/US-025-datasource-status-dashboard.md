# US-025：資料來源狀態監控儀表板

> **Story ID**：US-025
> **Epic**：[E03 — 資料來源管理](epic-brief.md)
> **優先級**：Should Have
> **階段**：Phase 1（MVP）
> **預估點數**：8

---

## User Story

**As a** Admin（管理者）
**I want** 查看顯示所有已設定資料來源健康狀態的儀表板
**So that** 我可以快速識別連線問題，並監控整體資料整合的健康狀況

---

## 驗收標準

### AC-1：儀表板總覽
- **Given** Admin 導覽至資料來源狀態監控儀表板
- **When** 頁面載入完成
- **Then** 系統顯示摘要卡片，包含：資料來源總數、已連線數量、已中斷數量、未知／從未測試數量

### AC-2：個別狀態顯示
- **Given** 儀表板已載入完成
- **When** Admin 瀏覽儀表板
- **Then** 每個資料來源顯示：名稱、類型、目前狀態（顏色標記：綠色=已連線、紅色=已中斷、灰色=未知）、最後測試時間、以及「立即測試」快捷按鈕

### AC-3：自動健康檢查
- **Given** 系統中有已設定的資料來源
- **When** 距離上次自動檢查已過 30 分鐘
- **Then** 系統自動對所有資料來源執行連線測試，更新各資料來源的狀態與 `lastTestedAt`，儀表板即時反映最新結果

### AC-4：連線效能趨勢圖
- **Given** 儀表板已載入完成，且資料來源有歷史健康檢查紀錄
- **When** Admin 點擊某資料來源或查看趨勢圖區塊
- **Then** 系統顯示折線圖，X 軸為時間、Y 軸為回應時間（ms），預設顯示最近 24 小時的資料，並可切換為 7 天或 30 天範圍

### AC-5：來源類型圓餅圖
- **Given** 儀表板已載入完成
- **When** Admin 瀏覽儀表板
- **Then** 系統顯示圓餅圖，依資料來源類型（MySQL、PostgreSQL、SQL Server）分類顯示各類型的數量與佔比百分比

### AC-6：健康檢查告警列表
- **Given** 儀表板已載入完成
- **When** 有資料來源連續 2 次以上健康檢查失敗（連續 2 個週期，即 60 分鐘內）
- **Then** 系統在告警列表中顯示該資料來源，包含：名稱、類型、連續失敗次數、首次失敗時間、最近失敗訊息，依連續失敗次數由高到低排序

### AC-7：手動重新整理
- **Given** Admin 在儀表板頁面
- **When** Admin 點擊「全部重新整理」或特定資料來源的「立即測試」按鈕
- **Then** 系統重新測試選定的連線，並在不重新載入頁面的情況下即時更新狀態

---

## Technical Notes

- 端點：`GET /api/datasources/dashboard`
- Response：`{ summary: { total, connected, disconnected, unknown }, datasources: [...] }`
- 「全部重新整理」觸發所有資料來源的平行連線測試
- 使用 WebSocket 或 Polling 機制實作大量測試期間的即時狀態更新
- 儀表板必須在 2 秒內載入完成（依 NFR-002 規範）
- 顏色標記：已連線（#22C55E）、已中斷（#EF4444）、未知（#9CA3AF）
- 後端排程：每 30 分鐘自動執行一次所有資料來源的連線健康檢查（使用 cron job 或類似機制）
- 自動檢查與手動「全部重新整理」共用相同的測試邏輯（`POST /api/datasources/:id/test`）
- 前端儀表板透過 Polling（建議 30 秒間隔）或 WebSocket 取得最新狀態
- 軟刪除的資料來源（`deleted_at IS NOT NULL`）排除在自動健康檢查範圍外
- 效能趨勢圖端點：`GET /api/datasources/:id/metrics?range=24h|7d|30d`
- Response：`{ datapoints: [{ timestamp, responseTimeMs, success }] }`
- 每次健康檢查需記錄 `responseTimeMs` 至歷史紀錄表（如 `datasource_health_logs`）
- 來源類型圓餅圖：從 `GET /api/datasources/dashboard` 的 summary 中擴充 `typeCounts: { mysql, postgresql, sqlserver }` 欄位
- 告警列表端點：`GET /api/datasources/alerts`
- 告警條件：連續 2 次以上健康檢查失敗（基於 `datasource_health_logs` 計算）
- 告警列表依連續失敗次數降冪排序
- 當資料來源恢復連線（健康檢查成功），自動從告警列表移除

## 測試案例

| # | 測試案例 | 預期結果 |
|---|---------|---------|
| 1 | 載入含混合狀態的儀表板 | 摘要數量正確，顏色標記正確 |
| 2 | 所有資料來源均已連線 | 全部顯示綠色，摘要相符 |
| 3 | 部分資料來源已中斷 | 顯示紅色標記，數量正確 |
| 4 | 尚未設定任何資料來源 | 顯示空狀態，含新增連結 |
| 5 | 點擊單一資料來源「立即測試」 | 狀態即時更新 |
| 6 | 點擊「全部重新整理」 | 所有狀態重新測試並更新 |
| 7 | 等待 30 分鐘後檢查 | 所有資料來源的狀態與 lastTestedAt 自動更新 |
| 8 | 軟刪除的資料來源 | 不出現於儀表板，不納入自動檢查 |
| 9 | 查看某資料來源 24 小時趨勢圖 | 折線圖正確顯示回應時間變化 |
| 10 | 切換趨勢圖至 7 天範圍 | 圖表更新為 7 天資料 |
| 11 | 無歷史紀錄的資料來源趨勢圖 | 顯示「尚無資料」提示 |
| 12 | 來源類型圓餅圖 | 各類型數量與佔比正確 |
| 13 | 僅有單一類型的圓餅圖 | 顯示 100% 單一類型 |
| 14 | 資料來源連續 2 次檢查失敗 | 出現於告警列表 |
| 15 | 資料來源恢復連線 | 自動從告警列表移除 |
| 16 | 告警列表排序 | 依連續失敗次數由高到低 |
| 17 | 儀表板載入時間 | 在 2 秒內完成渲染 |
| 18 | 非 Admin 存取 | 回傳 403 Forbidden |

## Definition of Done

- [ ] 儀表板頁面含摘要卡片
- [ ] 個別資料來源狀態卡片／列表
- [ ] 顏色標記的狀態指示
- [ ] 每個資料來源的「立即測試」按鈕
- [ ] 含平行測試的「全部重新整理」按鈕
- [ ] 後端每 30 分鐘自動健康檢查排程實作完成
- [ ] 軟刪除資料來源排除在自動檢查外
- [ ] 連線效能趨勢折線圖（支援 24h / 7d / 30d 切換）
- [ ] 健康檢查歷史紀錄表（`datasource_health_logs`）寫入與查詢
- [ ] 來源類型圓餅圖（MySQL / PostgreSQL / SQL Server 佔比）
- [ ] 健康檢查告警列表（連續 2 次失敗觸發，恢復後自動移除）
- [ ] 即時狀態更新（無需重新載入整頁）
- [ ] 儀表板在 2 秒內載入完成
- [ ] 空狀態正確處理
- [ ] 所有驗收標準的單元測試通過
