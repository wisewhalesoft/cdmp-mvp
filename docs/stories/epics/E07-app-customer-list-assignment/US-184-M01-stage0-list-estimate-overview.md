# US-184：Stage 0 試算頁新增「名單基礎預估數量總覽」（按產品類別分組小計）

> **Story ID**：US-184
> **Epic**：[E07 — 客戶名單分派](epic-brief.md)
> **模組**：M01 名單定義（Stage 0 試算頁，F049 v2.0 頁面之新增區塊）
> **優先級**：Should Have
> **階段**：Phase 2（Advanced，既有 F049 v2.0 部門化重設計之能力擴充）
> **預估點數**：8
> **對應 Feature**：F120（由 spec-writer 建立，非本 Story 範圍）

---

## 背景說明

Stage 0 試算頁（`/assignment/estimate`，`prototypes/30-stage0-estimate.html`）現況提供兩個以**部門**為維度的區塊：「部門負載總覽」（各部門本月合計件數、人均負荷、負載狀態）與「部門每日分派明細」（月曆呈現各部門每日預估件數）。這兩者回答的問題是「哪個部門忙不過來」。

業務部長 / Admin 在檢視這兩個部門區塊之前，往往需要先確認「這個月到底跑了哪幾份名單、每份名單各自估出多少件、是被什麼條件篩出來的」——這件事目前無法在試算頁一次看完，必須逐一切換「名單篩選」下拉、一份一份點開才能拼湊全貌。本 Story 新增第三個區塊「名單基礎預估數量總覽」，直接列出本月所有納入試算的名單，並以產品類別（汽車 / 機車 / 一般商品）分組小計，讓部長在部門維度之外，先掌握「名單維度」的組成與量體。

**與既有頁面的關係**：本區塊不是新頁面、不是新端點族，而是同一顯示模式（全名單彙總 / 單一名單鑽探，US-166）、同一名單集合（當月 `status='active'` 名單，US-167 §16 起算之 L1 `list_total[L]`）之上的第三種呈現角度。已完成之 F049 v2.0 Part B（§14~§22：US-166 彙總層 / US-167 部門投影 / US-168 處長 scope / US-169 可行性 / US-170 術語清理）為本 Story 的既有基礎，須先讀過再動筆。

**重要現況查證（直接影響 AC-LIST-06 之分組歸屬規則設計）**：`ob_list_definition.prod_kind`（`apps/api/src/database/entities/ob-list-definition.entity.ts:87-88`）自 F050 v2.1（AD-E07-18）起已**不是**可直接讀取的產品類別欄位，而是由 `condition_payload` 衍生之 backward-compat 欄位（`assignment-list.service.ts:605-648` `deriveBackwardCompatColumns()`）：
- 當名單以 `IN` 核取清單設定 `prod_kind` 條件、且勾選多個值時，衍生結果是 `values.join('$$')`（如 `"01$$02"`），**不是單一類別**。
- 當名單以 F119（US-183）新增的文字運算子（包含／不包含／完全等於）設定 `prod_kind` 條件時，`cond.values` 為 `undefined`（文字運算子改用 `keyword`），衍生邏輯 `if (cond.fieldType === 'categorical' && Array.isArray(cond.values))` 不成立，**衍生結果恆為空字串 `''`**——即使名單其實有設定產品類別篩選，衍生欄位也看不出來。
- 當名單完全未設定 `prod_kind` 條件時，衍生結果同樣是空字串 `''`。

三種情況（多值、文字運算子、未篩選）在 `prod_kind` 欄位上**表面結果無法區分**（多值是非空但含 `$$`，其餘兩種都是空字串）。因此本區塊的分組依據**不可**直接讀取 `ob_list_definition.prod_kind` 這個 backward-compat 欄位，必須回頭解析 `condition_payload.conditions[columnName='prod_kind']` 本身——但這已經涉及「多值名單該歸哪一組」「文字運算子名單該歸哪一組」的業務判斷，非純技術問題，見 AC-LIST-06。

---

## User Story

**As a** 業務部長（Director）或 Admin，在觸發月名單分派前檢視 Stage 0 試算頁
**I want** 在既有的「部門負載總覽」「部門每日分派明細」之外，看到一份以名單為單位、按產品類別分組小計的總覽表（名單編號 / 名單名稱 / 篩選條件 / 預估數量）
**So that** 我可以在動手拆解到部門負載之前，先確認「這個月到底跑了哪些名單、量體如何分佈在汽車／機車／一般商品之間」，快速抓出漏設、誤設或量體異常的名單，而不必逐一點開名單篩選器一份一份核對

## 驗收標準

### AC-LIST-01：新增「名單基礎預估數量總覽」區塊

- **Given** 業務部長 / Admin 於 `/assignment/estimate` 檢視 Stage 0 試算頁，且當月（試算作業月份）有至少一筆 `status='active'` 的 `ob_list_definition`
- **When** 頁面載入完成
- **Then** 頁面在既有「部門負載總覽」「部門每日分派明細」之外，新增第三個區塊「名單基礎預估數量總覽」，呈現於這兩個既有區塊之後、頁尾提示（footer note）之前
- **And** 確切的區塊間視覺排序（例如是否改置頂）由 ui-ux-designer 於 prototype 定案，本 AC 僅約束「新增一個獨立區塊、不得混入既有兩區塊的表格結構」

### AC-LIST-02：資料範圍與既有兩區塊一致（同一名單集合、隨篩選器連動）

- **Given** 試算頁目前的顯示模式（US-166：全名單彙總 或 單一名單鑽探）與試算作業月份
- **When** 「名單基礎預估數量總覽」區塊渲染
- **Then** 本區塊之名單集合**必須**與同頁「部門負載總覽」「部門每日分派明細」使用的名單集合完全一致（當月 `status='active'` 之 `ob_list_definition`，不因 `stage`（draft/dept_ratio/personnel_ratio/approval/ready）而排除，與 US-167 §16 起算之 L1 名單集合相同）
- **And** 使用者切換頁面既有的「名單篩選」下拉（全部名單 / 單一名單）時，本區塊同步縮限為對應集合（單一名單模式下僅顯示該 1 筆名單），與部門兩區塊的鑽探行為一致（US-166 AC-2/AC-3）
- **And** 使用者切換試算作業月份時，本區塊隨之重新計算（比照 US-166 AC-5）

### AC-LIST-03：每筆名單顯示四項資訊

- **Given** 本區塊已渲染名單集合
- **When** 使用者檢視任一名單列
- **Then** 每列至少顯示：名單編號（`list_no`）、名單名稱（`list_nm`）、篩選條件（見 AC-LIST-04）、預估數量（見 AC-LIST-09 之資料來源）
- **And** 「預估數量」之數值來源與同頁其他區塊之 L1 名單總量口徑**必須一致**（同一份 `list_total[L]`：優先取 `stage0_estimate_count` 物化快取，缺值時 fallback 完整 Stage 1 dry-run，見 `stage0-estimate.service.ts:545-573`），不得另開一套獨立估算邏輯，否則會與部門區塊的合計數字互相矛盾

### AC-LIST-04：篩選條件欄位重用既有唯一格式化來源

- **Given** 某名單有一或多筆 `condition_payload.conditions`
- **When** 本區塊渲染該名單之「篩選條件」欄位
- **Then** 呈現方式須重用既有全站唯一格式化來源（`apps/web/src/pages/assignment/_utils/condition-summary.ts` 之 `formatConditionSummary()`，已用於名單詳情 Drawer 與名單定義列表 Kanban 卡片），不得另開第三套字串拼接邏輯，以維持 BR-10「單一格式化來源」不變式
- **And** 一份名單通常有多筆條件（AND 語意），欄位須完整呈現全部條件（而非僅 `prod_kind` 這一筆）；條件數量多、文字過長時的截斷 / hover 展開樣式由 ui-ux-designer 定案（見待解決問題 OQ-184-03，non-blocking）
- **And** 條件為空（`condition_payload IS NULL` 或 `conditions=[]`）時，比照既有規則顯示「（未設定篩選條件）」或等義文案，不得顯示為空白

### AC-LIST-05：以產品類別分組，分組標籤重用既有 decode 機制

- **Given** 名單集合中每筆名單依 AC-LIST-06 之規則被歸入某個產品類別分組
- **When** 本區塊渲染分組標題
- **Then** 分組標題文字（汽車 / 機車 / 一般商品）須透過既有 `pooldata_field_option`（`column_name='prod_kind'`）decode 機制取得（前端沿用 `useConditionDecoder().decodeValue('prod_kind', code)` 或後端等義查表），**不得**在本區塊硬編碼中文標籤字串
- **And** 此要求之理由：若日後業務新增第 4 種產品類別（如新增 `04` 代碼），分組標題須自動反映白名單異動，不需改本區塊程式碼

### AC-LIST-06：多值 / 文字運算子 / 未篩選名單之分組歸屬規則（定案，2026-08-20 業務主管裁決，OQ-184-01）

- **Given** 名單之 `condition_payload.conditions` 中 `columnName='prod_kind'` 的條件項目（若存在）
- **When** 本區塊決定該名單歸入哪個分組
- **Then**（**定案規則，不再列為待確認**）：
  - 該條件為 `IN` 運算子且 `values` 恰為**單一**代碼（`01` / `02` / `03` 之一）→ 歸入對應之汽車／機車／一般商品分組
  - 該條件為 `IN` 運算子且 `values` 含**兩個以上**代碼（如同時勾選 `01` 與 `02`）→ 歸入獨立分組「多重產品類別」，**不得**同時計入汽車與機車兩組（避免同一筆名單的預估數量被重複計入兩個小計，破壞 AC-LIST-09 之總計不變量）
  - 該條件為任一文字運算子（包含／不包含／完全等於，F119）→ 因比對結果無法在不查詢資料的前提下事先歸類為某個固定代碼，歸入「未分類」分組
  - 名單完全未設定 `prod_kind` 條件 → 歸入「未分類」分組
- **And** 「多重產品類別」與「未分類」兩個分組固定排在汽車／機車／一般商品三組之後（順序見 AC-LIST-07），且兩者為**不同**分組、不得合併顯示，以便業務區分「有意跨類別」與「根本沒設類別」兩種情境
- **And**（**互斥且完備不變量，可測，AC-LIST-09 總計不變量之前提**）：任一參與計算之名單（估算逾時名單依 AC-LIST-10 另計，不受本不變量約束），在同一時刻**恰好**屬於「汽車」「機車」「一般商品」「多重產品類別」「未分類」五個分組中的**一個**——不得同時計入兩個分組，也不得不屬於任何分組。此不變量為 AC-LIST-09「各組小計加總＝總計」得以成立之前提，任何分組邏輯之技術實作變更皆不得破壞此不變量
- **And** 本規則為業務主管已裁決之最終行為（見待解決問題 OQ-184-01 裁決記錄），非本 Story 之建議或待確認事項；日後若業務要求改變（例如多值名單重複計入每個符合類別），須另立 Story 或明確變更本 AC 與 AC-LIST-09 之不變量描述，不得由下游 agent 逕自解讀為仍待確認

### AC-LIST-07：組間與組內排序

- **Given** 分組已依 AC-LIST-06 決定
- **When** 頁面渲染分組順序
- **Then** 組間順序固定為：汽車 → 機車 → 一般商品（依 `pooldata_field_option` 既有登錄順序 `01`/`02`/`03`）→ 多重產品類別 → 未分類
- **And** 每個分組內之名單列依名單編號（`list_no`）遞增排序，與既有名單定義列表排序慣例一致

### AC-LIST-08：分組小計內容（含佔比，定案，2026-08-20 業務主管裁決，OQ-184-04）

- **Given** 每個分組內已列出所屬名單
- **When** 使用者檢視分組小計列
- **Then** 每個分組底部（或標題列）顯示三項：(1) 該組名單數（筆）、(2) 該組預估數量小計（件，Σ 該組內各名單之 AC-LIST-03 預估數量，估算逾時名單依 AC-LIST-10 排除）、(3) 該組**佔總計之百分比**
- **And**（**佔比計算定義，定案**）：
  - 分母：AC-LIST-09 之「預估數量總計」（已依 AC-LIST-10 排除估算逾時名單）
  - 分子：該組預估數量小計（同上，同樣已排除估算逾時名單）
  - 顯示格式：四捨五入至**整數**百分比，不顯示小數位（例如 42%）
  - **總計為 0** 時（例如當月所有名單全數估算逾時，導致「預估數量總計」= 0）：所有分組之佔比一律顯示「—」，**不得**顯示 `0%`、`NaN` 或 `Infinity`
  - 各組百分比經四捨五入後加總**可能不等於 100%**（例如三組分別捨入為 33%/33%/34%=100%，或 33%/33%/33%=99%），此為**預期之四捨五入行為**，**不強制湊整**（不採最大餘數法、不由最後一組吸收誤差等技術修正手段），下游 QA / 使用者回報「百分比加總非 100%」時，**非缺陷**
- **And** 空分組（該組內無任何名單，例如當月完全沒有名單勾選機車）**不顯示**該分組（比照既有頁面「整期 0 件部門隱藏」之呈現慣例，避免大量空分組佔版面），故不會出現「0 名單卻仍顯示 0%」之情形
- **And** 單一名單鑽探模式下（AC-LIST-09 總計退化為該名單自身之預估數量），佔比欄位是否顯示（例如固定顯示 100%，或該模式下直接隱藏佔比欄）由 ui-ux-designer 定案，非阻塞項

### AC-LIST-09：總計列與跨區塊一致性不變量

- **Given** 各分組小計已計算完成
- **When** 使用者檢視本區塊底部總計列
- **Then** 顯示「名單總數」（Σ 各分組名單數）與「預估數量總計」（Σ 各分組預估數量小計）
- **And**（**跨區塊一致性不變量，必須成立**）：全名單彙總模式下，「預估數量總計」須與同頁「部門負載總覽」/ KPI 卡片之「本月全名單總量」（`orgMonthTotal` = Σ 各名單 `list_total[L]`）**數值相等**——兩者本質上是同一份 L1 資料的兩種呈現角度，不容許出現「這裡看到的總量」與「部門那邊看到的總量」對不上的情況
- **And**（**與 AC-LIST-06 之關聯，必須成立**）：「各分組預估數量小計加總」須恰好等於「預估數量總計」（Σ 分組小計 = 總計，不多不少）——此不變量成立之前提是 AC-LIST-06 之「互斥且完備」分組規則（每筆計入總計的名單恰好落在一個分組），若分組邏輯之技術實作導致任何名單被重複計入或遺漏，即違反本 AC，須視為缺陷
- **And** 單一名單鑽探模式下，「預估數量總計」須等於該筆名單自身之預估數量（總計列此時退化為單一名單值，不顯示分組結構，或顯示僅含一組一列，由 ui-ux-designer 定案是否簡化呈現）

### AC-LIST-10：名單估算逾時之呈現（沿用既有 warning 機制）

- **Given** 某名單於個別估算查詢逾時，後端已依既有邏輯產生 `STAGE0_LIST_ESTIMATE_PARTIAL` warning（`stage0-estimate.service.ts:557-570`），且該名單已被排除於 `listTotals` 之外
- **When** 本區塊渲染該名單所屬列
- **Then** 該名單仍列於清單中（讓使用者知道「這份名單存在、但這次沒能估出量」），其「預估數量」欄顯示「—」而非 0 或空白，並帶有與同頁既有逾時提示一致的視覺標記（沿用既有 `hourglass` 圖示 / 琥珀色警示語彙，US-183 AC-11 已建立之呈現慣例）
- **And** 該名單**不**計入所屬分組之小計、也不計入 AC-LIST-09 之總計（與部門區塊排除該名單之邏輯一致，維持跨區塊總量對得上）
- **And** 若該名單所屬分組因此變成「組內名單全數逾時、小計為 0」，分組本身仍需顯示（不可因小計為 0 而誤判為空分組隱藏），並在分組層級也標示「本組合計未涵蓋估算逾時之名單」提示

### AC-LIST-11：權限與 scope（定案，2026-08-20 業務主管裁決，OQ-184-02）

- **Given** 目前登入角色為業務處長（section_chief，唯讀）
- **When** 該角色檢視 Stage 0 試算頁
- **Then**（**定案規則，不再列為待確認**）：比照 F049 §17 BR-12 既有先例——單一名單 COUNT 端點（`GET /assignment/list-definitions/:listNo/estimate`）已對處長開放且回傳「名單層總量」（非部門分解）——本區塊性質同屬「名單層總量」而非「部門分解」，本 Story 開放：處長可見本區塊**完整內容**（全部 active 名單清單、其篩選條件、其預估數量、分組小計與總計），**不**依處長轄區部門限縮名單集合
- **And**（**誤讀風險，必須以 UI 明確標示，非僅文件敘述**）：此開放與現行「部門負載總覽」「部門每日分派明細」兩區塊對處長的隔離方式**不同**——那兩區塊對處長强制限縮為僅其轄區部門、且不顯示全部門合計（US-168 AC-2）；本區塊處長看到的是「全公司名單層總量」，非其轄區之分派量。為避免處長誤讀為「這是我轄區要處理的量」，本區塊在處長角色下**必須**呈現明確語意標示（例如區塊標題旁或說明文字：「本區塊為全公司名單層總量，非您所屬轄區之分派量」或等義文案），確切文案與呈現位置由 ui-ux-designer 定案（見待解決問題 OQ-184-03）
- **And** 此語意標示為 AC 之必要條件（Then 子句一部分），若處長角色下本區塊未帶此標示即渲染完整內容，視為未通過本 AC，不得以「反正資料正確」為由略過

### AC-LIST-12：當月無 active 名單之空狀態

- **Given** 當月無任何 `status='active'` 的 `ob_list_definition`
- **When** 頁面載入
- **Then** 「名單基礎預估數量總覽」區塊顯示與同頁既有空狀態一致之提示文案（比照 US-166 AC-4：「本月尚無啟用名單，請先於名單定義頁建立並啟用名單」），不渲染任何分組或表格列

### AC-LIST-13：試算僅為預覽，不寫入任何分派資料

- **Given** 本區塊顯示計算結果
- **When** 計算完成
- **Then** 系統**不**寫入 `ob_pool_data_list`、`assignment_run` 或任何分派紀錄（與 US-166 AC-6 / F049 BR-1 一致，estimate ≡ run invariant 於唯讀層維持）

### AC-LIST-14：術語清理，不得出現技術詞

- **Given** 本區塊任意可見文字（欄位名、分組標題、提示訊息）
- **When** 全文掃描
- **Then** 不得出現 F049 §19.1 已定義之技術詞黑名單（如 `ob_pool_data`、`ratioPerMille`、`rest_flg`、內部欄位名、資料表名、API 路徑等），維持與同頁其他區塊一致的業務語言（US-170 AC-TERM-1 之延伸要求）

### TC-184-01：新增區塊出現且位於既有兩區塊之後

- **Given**：當月有 3 筆 active 名單
- **When**：業務部長開啟試算頁
- **Then**：頁面除「部門負載總覽」「部門每日分派明細」外，另可見「名單基礎預估數量總覽」區塊

### TC-184-02：切換名單篩選器時本區塊同步縮限

- **Given**：頁面處於全名單彙總模式，本區塊顯示 3 筆名單
- **When**：使用者於名單篩選器選取其中 1 筆名單
- **Then**：本區塊僅顯示該 1 筆名單，分組結構相應簡化（見 AC-LIST-09 單一名單情境）

### TC-184-03：單一代碼名單正確歸入對應分組

- **Given**：名單 A 之 `condition_payload` 含 `columnName='prod_kind', operator='in', values=['01']`
- **When**：本區塊渲染
- **Then**：名單 A 出現於「汽車」分組

### TC-184-04：多值名單歸入「多重產品類別」，不重複計入單一類別分組

- **Given**：名單 B 之 `prod_kind` 條件為 `values=['01','02']`
- **When**：本區塊渲染
- **Then**：名單 B 僅出現於「多重產品類別」分組一次，不同時出現在「汽車」與「機車」分組

### TC-184-05：文字運算子名單與未篩選名單皆歸入「未分類」

- **Given**：名單 C 之 `prod_kind` 條件為 `operator='contains', keyword='02'`；名單 D 完全未設定 `prod_kind` 條件
- **When**：本區塊渲染
- **Then**：名單 C 與名單 D 皆出現於「未分類」分組

### TC-184-06：分組標題文字來自白名單 decode，非硬編碼

- **Given**：`pooldata_field_option` 中 `prod_kind='01'` 之 `option_label` 為「汽車」
- **When**：本區塊渲染「汽車」分組標題
- **Then**：標題文字與 `pooldata_field_option` 當下登錄值一致（regression：修改 seed label 後畫面同步反映，而非固定字串）

### TC-184-07：跨區塊總量一致性

- **Given**：全名單彙總模式，「部門負載總覽」KPI 卡片顯示「本月全名單總量」= 28,500
- **When**：檢視「名單基礎預估數量總覽」之總計列
- **Then**：「預估數量總計」同為 28,500

### TC-184-08：估算逾時名單顯示「—」且不計入小計與總計

- **Given**：名單 E 估算逾時，後端已產生 `STAGE0_LIST_ESTIMATE_PARTIAL` warning
- **When**：本區塊渲染
- **Then**：名單 E 該列「預估數量」顯示「—」並帶逾時視覺標記；其所屬分組小計與區塊總計皆不含名單 E 之數值

### TC-184-09：空分組不顯示

- **Given**：當月所有 active 名單皆為汽車或機車類別，無「一般商品」名單
- **When**：本區塊渲染
- **Then**：「一般商品」分組整組不顯示，不留空白區塊

### TC-184-10：當月無 active 名單顯示空狀態

- **Given**：當月無任何 active 名單
- **When**：頁面載入
- **Then**：本區塊顯示空狀態提示文案，不渲染表格或分組

### TC-184-11：試算不寫入任何分派紀錄

- **Given**：本區塊已顯示計算結果
- **When**：查詢 `ob_pool_data_list`、`assignment_run` row count
- **Then**：與試算前相同，無新資料寫入

### TC-184-12：篩選條件欄位重用既有格式化來源，非另拼字串

- **Given**：名單 F 條件為「主約專案名稱 包含「勁便利」」+「職業別：業務、行政」
- **Then**：本區塊「篩選條件」欄位顯示內容與名單詳情 Drawer / 名單定義列表 Kanban 卡片對同一名單之顯示文字**逐字元相同**

### TC-184-13：分組互斥且完備，名單不重複亦不遺漏

- **Given**：當月 5 筆 active 名單，分別對應「單一代碼」「多值代碼」「文字運算子」「未設定 `prod_kind`」「單一代碼」五種情境
- **When**：本區塊完成分組渲染
- **Then**：每筆名單在五個分組（汽車／機車／一般商品／多重產品類別／未分類）中**恰好**出現一次；跨所有分組之名單編號集合聯集，等於參與計算之名單全集（估算逾時名單除外），無重複、無遺漏

### TC-184-14：佔比正確計算（分母為總計，四捨五入至整數）

- **Given**：全名單彙總模式，「預估數量總計」= 10,000；「汽車」分組小計 = 4,200
- **When**：檢視「汽車」分組佔比
- **Then**：顯示 `42%`（4,200 ÷ 10,000 四捨五入至整數）

### TC-184-15：總計為 0 時佔比降級為「—」，不顯示 0% 或 NaN

- **Given**：當月所有 active 名單全數估算逾時（`STAGE0_LIST_ESTIMATE_PARTIAL`），「預估數量總計」= 0
- **When**：檢視任一（未被隱藏之）分組佔比
- **Then**：顯示「—」，不顯示 `0%`、`NaN` 或 `Infinity`

### TC-184-16：業務處長可見本區塊完整內容，且帶語意標示

- **Given**：登入角色為業務處長（section_chief），轄區為北區電銷一課
- **When**：該處長檢視 Stage 0 試算頁「名單基礎預估數量總覽」區塊
- **Then**：可見**全部**當月 active 名單（不限其轄區），分組小計與總計皆為全公司口徑，且區塊帶有明確語意標示（例如「本區塊為全公司名單層總量，非您所屬轄區之分派量」或等義文案），使處長不致誤讀為自身轄區工作量
