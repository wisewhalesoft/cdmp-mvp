# US-179：員工編號作為登入識別碼

> **Story ID**：US-179
> **Epic**：[E02 — 帳號與角色管理](epic-brief.md)
> **跨 Epic**：[E01 — 驗證與登入](../E01-auth-and-login/epic-brief.md)（登入識別碼比對邏輯擴充，見 US-001、US-002）
> **優先級**：Should Have
> **階段**：Phase 1（MVP）
> **預估點數**：5

---

## User Story

**As a** Admin（管理者）
**I want** 在建立或編輯使用者帳號時，選填設定該帳號的員工編號
**So that** 使用者除了 Email 外，也能以組織內部熟悉的員工編號作為登入識別碼，降低使用者記憶／輸入 Email 的負擔

*（第二視角，供理解完整價值鏈，不另立獨立 Story）*
**As a** 使用者（Admin 或 User）
**I want** 在登入時可以輸入我的 Email 或員工編號（擇一）加上密碼
**So that** 我不需要每次都記得或查找自己的 Email，也能順利登入 CDMP 平台

---

## 背景說明

目前（US-010／US-012）帳號僅有 Email 作為唯一登入識別碼。本 Story 新增一個**選填**的帳號屬性「員工編號」（`employee_no`），由 Admin 於帳號管理（建立／編輯）中設定；設定後，該帳號的使用者於登入頁面（US-001／US-002）可以輸入 Email 或員工編號（擇一，系統依輸入內容自動判斷）搭配密碼登入，兩種方式效果完全相同（發行相同規則的 Session Token、依角色導向相同頁面）。

員工編號設計為 Admin 專屬可維護欄位，使用者本身無法自助編輯（本 MVP 無使用者自助個人資料編輯功能，與現況一致）。是否設定員工編號完全選填，未設定的帳號僅能繼續以 Email 登入，行為與現況完全相同。

「忘記密碼」流程本次**不**納入員工編號支援，維持僅能以 Email 申請重設（見 AC-13、待解決問題 OQ-179-01）。

## 驗收標準

### AC-1：建立帳號時可選填員工編號
- **Given** Admin 在建立帳號表單，已填妥必填欄位（姓名、Email、密碼、角色）
- **When** Admin 於「員工編號」欄位輸入一個尚未被使用、格式合法的值（如「E12345」）後點擊「建立帳號」
- **Then** 系統建立帳號並儲存該員工編號，顯示成功訊息，新帳號出現於帳號清單中，員工編號正確顯示

### AC-2：建立帳號時員工編號為選填（可留空）
- **Given** Admin 在建立帳號表單，已填妥必填欄位
- **When** Admin 未填寫員工編號欄位，直接點擊「建立帳號」
- **Then** 系統成功建立帳號，該帳號的員工編號為空（null），不視為驗證錯誤

### AC-3：編輯帳號新增員工編號
- **Given** Admin 正在編輯一個目前未設定員工編號的既有帳號
- **When** Admin 於員工編號欄位輸入一個合法且未被使用的值後點擊「儲存」
- **Then** 系統更新該帳號的員工編號，顯示成功訊息，並立即反映於畫面

### AC-4：編輯帳號變更或清除員工編號
- **Given** Admin 正在編輯一個已設定員工編號的既有帳號
- **When** Admin 將員工編號改為另一個合法且未被使用的值，或將欄位清空後點擊「儲存」
- **Then** 系統依輸入結果更新該帳號的員工編號為新值，或清空為 null，顯示成功訊息並立即反映變更

### AC-5：防止重複員工編號 — 建立帳號
- **Given** 員工編號「E12345」已被帳號 A 使用
- **When** Admin 嘗試以員工編號「E12345」建立新帳號
- **Then** 系統顯示「此員工編號已被使用」錯誤訊息，且不建立該帳號

### AC-6：防止重複員工編號 — 編輯帳號（排除自身）
- **Given** 員工編號「E12345」已被帳號 A 使用，Admin 正在編輯帳號 B（另一帳號）
- **When** Admin 將帳號 B 的員工編號變更為「E12345」
- **Then** 系統顯示「此員工編號已被使用」錯誤訊息，且不儲存變更
- **And** 若 Admin 改為編輯帳號 A 本身，並保留其原有員工編號「E12345」不變（連同其他欄位一併儲存），系統視為合法，正常儲存（唯一性檢查排除自身帳號）

### AC-7：員工編號格式驗證
- **Given** Admin 在建立或編輯帳號表單填寫員工編號欄位
- **When** Admin 輸入的值包含「@」符號，或長度超過 32 字元，或包含英數字、`-`、`_` 以外的字元
- **Then** 系統顯示具體格式錯誤訊息（區分不同違規原因，如「不可包含 @」「長度不可超過 32 字元」「僅允許英數字、- 與 _」），且不建立／不儲存該帳號

### AC-8：員工編號前後空白自動去除
- **Given** Admin 在員工編號欄位輸入的值前後包含空白字元（如「 E12345 」）
- **When** Admin 提交表單
- **Then** 系統於驗證與儲存前自動去除首尾空白，以去除空白後的值（「E12345」）進行格式與唯一性驗證及儲存

### AC-9：Email 登入行為維持不變（回歸）
- **Given** 帳號（Admin 或 User）已設定 Email 與密碼，不論是否設定員工編號
- **When** 使用者在登入頁面的識別碼欄位（已由「Email」relabel 為「Email / 員工編號」）輸入含「@」的正確 Email 與正確密碼並點擊「登入」
- **Then** 系統判定輸入值含「@」，以既有 Email 比對邏輯（大小寫不敏感）驗證身份，發行 Session Token 並依角色導向對應頁面，行為與 US-001／US-002 完全一致，不受本 Story 影響

### AC-10：以員工編號成功登入
- **Given** 帳號（Admin 或 User）已設定員工編號「E12345」與密碼，帳號為有效且啟用中
- **When** 使用者在登入頁面的「Email / 員工編號」欄位輸入「E12345」（不含「@」）與正確密碼並點擊「登入」
- **Then** 系統判定輸入值不含「@」，以員工編號進行精確比對（區分大小寫，儲存值原樣比對）驗證身份，驗證成功後發行與 Email 登入相同規則的 Session Token，並依該帳號角色導向對應頁面（規則同 US-001／US-002）

### AC-11：不存在的員工編號或錯誤密碼 → 通用錯誤訊息（不洩漏資訊）
- **Given** 系統中不存在員工編號「E99999」；或帳號員工編號為「E12345」但使用者輸入錯誤密碼
- **When** 使用者以上述任一情境輸入識別碼與密碼並點擊「登入」
- **Then** 系統一律顯示與 Email 登入失敗相同的通用錯誤訊息「Email 或密碼錯誤」，不發行 Session Token，且不揭示是識別碼不存在還是密碼錯誤

### AC-12：帳號停用時以員工編號登入 → 沿用既有停用行為
- **Given** 帳號員工編號為「E12345」，且該帳號已被停用
- **When** 使用者以「E12345」與正確密碼登入
- **Then** 系統顯示「您的帳號已被停用，請聯絡管理員。」，且不發行 Session Token，行為與既有 Email 登入之停用帳號情境（US-001 AC-4／US-002 AC-4）一致

### AC-13：忘記密碼不支援員工編號，僅支援 Email
- **Given** 使用者在「忘記密碼」頁面（此頁面輸入欄位維持僅標示「Email」，不採用登入頁面之合併識別碼欄位）
- **When** 使用者於欄位輸入自己的員工編號（而非 Email）並點擊「發送重設連結」
- **Then** 系統將輸入值視為 Email 查找帳號；因員工編號格式不含「@」，不會比對到任何帳號的 Email，系統回傳與「Email 不存在」相同的通用成功訊息「若此 Email 存在，重設連結已寄出」（沿用 US-015 AC-2 不洩漏帳號是否存在原則），不寄出任何重設連結
- **（此為建議預設行為，非業務明確拍板，見待解決問題 OQ-179-01）**

### AC-14：帳號清單顯示員工編號欄位
- **Given** Admin 導覽至帳號管理頁面的帳號清單
- **When** 頁面載入完成
- **Then** 系統於清單欄位中新增「員工編號」欄，顯示各帳號的員工編號值；未設定員工編號的帳號該欄顯示為空白

### AC-15：帳號清單搜尋涵蓋員工編號
- **Given** Admin 正在查看帳號清單
- **When** Admin 於既有搜尋欄位輸入員工編號的全部或部分內容（如輸入「E123」）
- **Then** 系統搜尋範圍除既有姓名、Email 外，亦以大小寫不敏感、部分匹配方式比對員工編號欄位，清單更新僅顯示匹配的帳號（此搜尋比對規則與登入時「精確、區分大小寫」比對規則不同，屬清單查詢情境的獨立設計，見待解決問題 OQ-179-02）

### AC-16：僅 Admin 可設定／編輯員工編號（RBAC，沿用既有守衛）
- **Given** 非 Admin 使用者
- **When** 該使用者嘗試存取帳號管理頁面，或嘗試透過建立／編輯帳號 API 端點設定 `employeeNo`
- **Then** 系統依既有帳號管理 RBAC 機制回傳 403 Forbidden（沿用 US-010／US-012 既有守衛，本 Story 不新增守衛），一般使用者無法透過任何管道自助設定或編輯自己的員工編號

## 本 Story 不含的範圍（留給 spec / architect / TDD）

- `employee_no` 欄位之資料庫層唯一性約束實作方式（unique index、大小寫比對 collation 等）由 system-architect 決定
- 登入識別碼判斷邏輯（是否含「@」）之確切程式實作、與既有 Email 查找／密碼比對程式碼的整合方式由 spec-writer／system-architect 決定
- 格式錯誤訊息之確切文案、多重違規時的訊息呈現優先順序由 ui-ux-designer／spec-writer 決定
- 帳號清單「員工編號」欄位的版面配置、欄寬、是否可排序等視覺細節由 ui-ux-designer 決定
- 是否需要新增帳號建立完成通知機制（讓使用者主動得知自己的員工編號可用於登入）不在本 Story 範圍（見待解決問題 OQ-179-03）

## Technical Notes

- 受影響端點：`POST /api/accounts`（US-010／F004）、`PUT /api/accounts/:id`（US-012／F006）、`GET /api/accounts`（US-011）、`POST /api/auth/login`（US-001／US-002／F001／F002）
- 新增帳號欄位：`employee_no`（DB）／`employeeNo`（API），型別為字串，可為 null
- 建立／編輯帳號 Request body 新增可選參數 `employeeNo?: string`
- 帳號清單 Response 之帳號物件新增 `employeeNo` 欄位
- 登入 Request body 之識別碼欄位語意擴充（沿用既有 `email` 欄位名稱或改用通用 `identifier` 欄位名稱，由 spec-writer 決定命名）
- 密碼驗證、Token 發行、角色導向規則完全沿用 US-001／US-002 既有機制，不因識別碼類型而改變

## 待解決問題

- [ ] **OQ-179-01**：忘記密碼頁面輸入員工編號時，本 Story 建議沿用「Email 不存在」之通用成功訊息（不新增專屬提示文案）。是否需要更明確的提示文案（例如「員工編號無法用於重設密碼，請改用 Email」）？需業務／UX 確認，若採用專屬文案則需評估是否有洩漏帳號存在與否之風險。
- [ ] **OQ-179-02**：帳號清單「依員工編號搜尋」建議採「大小寫不敏感、部分匹配」（與既有姓名／Email 搜尋規則一致），但登入時的員工編號比對為「精確、區分大小寫」。兩種規則並存是否會造成使用者混淆（例如搜尋找得到、但登入卻打不進去）？需 UX 確認是否需要額外說明文案。
- [ ] **OQ-179-03**：帳號建立完成後，系統目前無主動通知使用者的機制（沿用 US-010 現況，不寄送帳號建立通知信）。使用者如何得知自己可用員工編號登入，需由 Admin 線下告知。是否需要在本 Story 或後續 Story 新增通知機制？
- [ ] **OQ-179-04**：員工編號是否需要與外部人資系統（HR／EMPHIRE 等）之員工編號欄位對應或驗證一致性？本 Story 假設為 Admin 手動輸入之自由格式字串，與既有 `ob_emphire`（在職資料）等來源表無關聯或比對，僅作為登入識別碼用途。若業務需要與人資系統對齊，需另立 Story 評估。

## Definition of Done

- [ ] 建立帳號表單新增員工編號欄位（選填）
- [ ] 編輯帳號表單支援新增／變更／清空員工編號
- [ ] 員工編號唯一性驗證（建立與編輯，編輯排除自身）
- [ ] 員工編號格式驗證（禁止 `@`、長度上限 32、僅允許英數字與 `-`／`_`、trim 空白）
- [ ] 登入頁面識別碼欄位 relabel 為「Email / 員工編號」
- [ ] 登入邏輯支援 Email 與員工編號擇一識別（含大小寫規則差異：Email 不敏感、員工編號精確比對）
- [ ] 登入失敗（不存在的識別碼／錯誤密碼）統一顯示通用錯誤訊息，不洩漏資訊
- [ ] 帳號停用情境下，以員工編號登入行為與既有 Email 登入一致
- [ ] 忘記密碼流程不受影響，員工編號輸入視為 Email 查無此帳號處理
- [ ] 帳號清單新增員工編號欄位顯示，並納入既有搜尋範圍
- [ ] RBAC：僅 Admin 可設定／編輯員工編號，沿用既有帳號管理守衛
- [ ] 所有驗收標準的單元測試通過
- [ ] 回歸測試：既有 Email 登入、Email 唯一性、帳號清單既有搜尋／篩選功能不受影響
